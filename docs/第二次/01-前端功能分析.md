## 1. 项目定位与运行形态

一句话：**规范化图片索引数据库 + 本地 Web 管理界面**。数据库才是本体，Web 界面是管索引和做人工审核的工具。

运行形态决定了前端的几个硬约束：

| 事实 | 对前端的影响 |
|---|---|
| 后端 FastAPI 单进程，`app/main.py` 直接托管 `frontend/dist` | 前端必须是**构建产物**形态（Vite build → dist），SPA history 回退由后端 `@app.get("/{full_path:path}")` 兜底 |
| 开发态走 Vite dev server（5173）+ `/api` 代理到 8321 | 前端不能写死 host，所有请求走相对路径 `/api/...` |
| 全部本机单机使用，无鉴权、无多用户 | 不需要登录/权限 UI，但需要**危险操作的二次确认** |
| 数据规模小（当前库内 10 张图、1 个登记目录）但量级可增长到万级 | 列表必须 cursor 分页/无限滚动，不能一次性全量渲染 |
| Python 侧的数据改动会即时反映到 SQLite | 前端任何写操作后要重新拉取，不做乐观的本地长期缓存 |

**当前真实库况**（`data/library.db`，用于后续所有 UI 决策）：
`images 10`、`hidden_images 0`、`directories 1`、`smart_albums 0`、`entities 0`、`rules 0`、`proposals 0`、`notices 37`、`trash 0`、`settings 70 行`；分析状态分布 `failed 7 / running 1 / skipped 2`；分类分布 `风景 3 / 人物 3 / 未分类 3 / 其他 1`。

> 注意这个分布：**失败 7 / 已真实成功 0**，也就是说当前界面上「失败态」是家常便饭而不是异常分支。重写必须让失败态可读、可重试、可解释，而不是一个小红点。

## 2. 后端能力全景（前端可调用的 60 个端点）

后端共 6 个路由模块、60 个 REST 端点。这是前端能画出来的全部地盘。

### 2.1 system.py（6 个）

| 方法 | 路径 | 用途 | 返回要点 |
|---|---|---|---|
| GET | `/api/health` | 存活探测 | `{status:"ok", version}` |
| GET | `/api/notices?limit=1..500` | 站内通知 | `{items:[{id,kind,level,message,read,created_at}]}` |
| DELETE | `/api/notices` | 清空通知 | `{cleared:true}` |
| GET | `/api/logs?lines=1..2000` | 日志尾 + 通知 + 级别 | `{lines:[...], notices:[...], level}` |
| GET | `/api/thumbs/{image_id}` | 缩略图二进制 | 404 若不存在 |
| POST | `/api/upload` | 单文件上传（multipart） | `{path, dir_id}`，自动登记 `data/uploads` 为来源目录 |

### 2.2 library.py（20 个）

目录侧：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/directories` | 目录列表，每项附带 `image_count` / `hidden_count` |
| POST | `/api/directories` | 两阶段登记：`?confirm=0`（默认）返回预估，`?confirm=1` 落库并立即扫描 |
| PATCH | `/api/directories/{id}` | 允许字段白名单：`recursive/enabled/offline/privacy/frozen/watcher/ocr_policy` |
| DELETE | `/api/directories/{id}` | 注销（只删索引，源文件不动） |
| POST | `/api/scan/{id}` | 增量扫描，返回 `added/updated/rebound/missing/skipped/scanned/excluded` |

图片侧：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/images` | 筛选列表，支持 `dir_id/category/tags/rating_min/favorite/date_from/date_to/analysis_state/sort/order/cursor/limit` |
| GET | `/api/hidden` | 隐藏区唯一入口（服务端强制 `hidden=true`，拒绝任何 `hidden/include_hidden/with_hidden/show_hidden` 查询参数） |
| GET | `/api/images/{id}` | 详情：基础行 + `manual_tags/ai_tags/elements/ocr_text/analyses/custom_fields/hidden/has_thumb/thumb` |
| PATCH | `/api/images/{id}` | 人工修正（写 `*_manual` 位，AI 位永不覆盖；支持 `tags`、`rating`、`favorite`、`notes`，以及同名自定义字段） |
| POST | `/api/images/{id}/hide` `/unhide` | 移入/移出隐藏区 |
| POST | `/api/images/{id}/redo` | 打回重识别，body `{feedback}`，计入 `correction_count` |
| POST | `/api/images/{id}/rename` | 改名，body `{name}`，禁止含分隔符、禁止同名覆盖、必须在已登记目录内 |
| POST | `/api/images/{id}/move` | 移动到另一登记目录，body `{dir_id}` |
| DELETE | `/api/images/{id}?mode=index\|source&confirm=` | `index` 只删索引并登记「仅移除索引」；`source` 源文件进回收站，确认词必须是文件名 |
| POST | `/api/images/batch` | `{op:"hide"\|"unhide"\|"delete"\|"patch", ids:[...], payload:{}}` |
| GET | `/api/images/{id}/similar?limit=1..100` | 以图搜图（向量；无向量时用描述兜底） |
| POST | `/api/export` | `{ids, format:"json"\|"csv"}` → `{path, count, format}`，可选剥离 EXIF 另存副本 |

检索侧：`GET /api/search`（多一个 `q` 和 `mode`）、`GET /api/search/history`、`DELETE /api/search/history`。

`/api/search` 返回结构值得单独拎出来，它是检索页信息架构的事实依据：

```jsonc
{
  "items": [ /* SELECT * FROM images 的全部列 + score + thumb */ ],
  "next_cursor": "...", "has_more": true,
  "mode": "hybrid", "degraded": false, "total": 12,
  "timings": { "total_ms": 12.3, "keyword_ms": 1.1, "vector_ms": 9.8 }
}
```

### 2.3 knowledge.py（21 个）

分类字典（CRUD，内置不可删改）、**实体资料库**（CRUD + 别名 + 参考图 + 关联图片，上限 2 参考图/实体、6 图总计、每次注入最多 3 实体）、**规则**（CRUD + `/api/rules/try` 试跑 + `/api/rules/recompute` 补算 pre/ocr）、**智能相册**（CRUD + `/api/albums/{id}/images` 回放）、**提案**（列表 + 批准/拒绝）、**自定义字段**（list/create/delete，类型 `text/number/date/select`）、**同义词组** `GET|PUT /api/synonyms`、**术语权重** `GET|PUT /api/term-weights`。

### 2.4 ops.py（9 个）

任务：`GET /api/jobs?state=`、`GET /api/jobs/{id}/events`、`POST /api/jobs/{id}/cancel|retry`、`DELETE /api/jobs`（清理已完成）。
统计：`GET /api/stats/dashboard`（`total/hidden/by_category/monthly/storage/states/tokens_total + jobs + dirs`）、`GET /api/stats/duplicates?perceptual=0|1&threshold=0..32`、`GET /api/stats/cleanup`（丢失文件/孤儿缩略图/回收站 50 条/建议）、`GET /api/stats/system`（`db_bytes/free_bytes/total_bytes`）。
回收站：`GET /api/trash`、`POST /api/trash/{id}/restore`、`DELETE /api/trash?confirm=清空回收站`。
危险操作：`POST /api/danger/clear-index`，body `{confirm:"清空索引"}`。

### 2.5 assistant.py（2 个）

`POST /api/chat`、`GET /api/chat?q=&limit=`，返回 `{answer, items, degraded, question, parsed:{keywords,category,date_from,date_to,rating_min}}`；软失败设计，不可用时返回引导语而不是报错。

### 2.6 settings.py（8 个）

`GET|PUT /api/settings`（schema 驱动：16 个分组 G1–G18、92 个配置项）、`POST /api/settings/test`（连接探测，可传 `base_url/api_key`，不传则按 `usage` 取已解析档案）、`GET /api/settings/audit?limit=`、`POST /api/settings/audit/{id}/rollback`、`GET /api/settings/profiles`、`POST /api/settings/profiles`、`DELETE /api/settings/profiles/{name}`、`POST /api/settings/backup`。

错误统一为 `{"error":{"code","message","detail"}}`，`data.error.message` 是可直接显示给用户的人话。

## 3. 现有前端架构现状

```
frontend/
├── index.html            12 行
├── vite.config.js        14 行（代理 /api → 8321，outDir=dist）
├── package.json          只有 vue + vue-router + @vitejs/plugin-vue + vite
└── src/
    ├── main.js            6 行
    ├── router.js         35 行（13 条路由，全量静态 import，无懒加载）
    ├── api.js            67 行（request 封装 + toast reactive + thumbUrl）
    ├── App.vue          120 行（侧栏 + <router-view> + toast）
    ├── styles.css       455 行（唯一样式源，全局裸 class，无令牌分层）
    ├── components/
    │   ├── ImageCard.vue      37 行
    │   └── ImageDrawer.vue   236 行
    └── pages/           12 个页面，共 1898 行
        Gallery 346 / Settings 316 / Rules 199 / Entities 190 / Dashboard 175
        Jobs 149 / Search 116 / Albums 119 / Chat 84 / Hidden 74 / Proposals 63 / Trash 67
```

**形态**：Vue3 `<script setup>` + Options-free Composition API，无状态管理库（各页面自持 `ref`），无 UI 组件库（纯手写 CSS），无 TypeScript，无 lint 门禁，无单元测试。

### 3.1 值得保留的东西

1. **`api.js` 的错误规范化思路**：统一从 `data.error.message` 取人话，附 `err.code` / `err.status`——这是全站「后端报错直接可读」的基础。
2. **toast 单例**：`reactive({items:[]})` + `notify()`，4 秒自动消失，跨页面共用。
3. **设置页 schema 驱动渲染**：新增配置项前端零代码，这条设计原则必须继承。
4. ** Gallery 两阶段登记向导的降级路径**：`409` 时自动降级为「已存在则增量扫描」，这是真实踩过坑的处理。

### 3.2 架构层面的问题

| 问题 | 具体表现 | 影响 |
|---|---|---|
| **无设计令牌分层** | `styles.css` 里 `:root` 定义 15 个变量，但大量样式直接写死颜色（`#fff`、`#f59e0b`）、写死尺寸（`width:110px`、`max-height:320px`），`.card .desc` 用 `height:1.4em` 定高截断 | 换肤几乎不可能；暗色模式下多处会露白或反色失败 |
| **类名全局裸放** | `.panel` `.card` `.row` `.field` `.tag` 无任何作用域隔离，只能在单个 `<style>` 里靠书写顺序博弈 | 任何新页面都可能被旧样式污染，反之亦然 |
| **重复布局代码** | `.page-head` + `.panel` + `table` 的骨架在 12 个页面里复制了 12 遍，`<ImageDrawer>` 在 Gallery/Search/Albums/Hidden/Chat 五处重复挂载且各自带不同的 `@changed` 语义 | 改一个视觉细节要动十几个文件 |
| **状态管理缺失** | `App.vue` 通过 `<router-view :settings="settings">` 向所有页面透传设置；页面自己又各自 `api.get("/api/settings")` 拉一遍（Gallery 单独拉 `watcher_enabled`，Settings 自己再拉一次） | 同一份数据 N 份副本，改了设置别处不刷新；App 的 `:settings` prop 靠 12 个页面各自声明才不报 warning |
| **router 无懒加载、无标题、无 meta** | 13 条路由全静态 import，无 `scrollBehavior`，无 `<title>` 维护 | 首屏打包全部页面；浏览器历史里所有标签都叫同一个名字 |
| **轮询缺乏治理** | `App.vue` 每 5 秒拉 jobs+proposals，`Jobs.vue` 每 3 秒刷全表，`setInterval` 写在组件里但页面停在前台才算；`Hidden.vue` 的 `load()` 没有 try/catch | 后台标签页堆叠请求；jobs 页面离开路由仍在轮询（未 `clearInterval` 的路径存在风险）；接口一挂就是整页空白 |
| **错误边界缺失** | 除 Gallery 少数地方外，绝大多数 `await api.get()` 直接裸写 | 后端没起 / 请求失败时页面整块白屏，用户不知道发生了什么 |

### 3.3 功能层面的缺陷

**P0 —— 用起来会卡住或误操作**

1. **Gallery 没有多选的一致语义**：勾选态用 `selected` Set，但「全选当前页」没有入口，「清空选择」要靠手动取消勾选。
2. **批量操作后分页状态丢失**：`batch()` 之后一律 `load(true)` 回到首页，用户在第 8 页做了操作会被弹回第 1 页，选中的也全没了。
3. **ImageDrawer 的删除确认词体验错配**：要求输入**完整文件名**（服务端规则），但 placeholder 写的是 `输入 ${filename} 确认` 而按钮文案是「删除」——一旦失败用户不知道要输什么。
4. **ImageDrawer 用 `window.prompt` 做打回反馈**：浏览器原生弹窗，样式不可控、不可 Esc 记忆输入、移动端等于没有。
5. **ImageDrawer 的相似图点击会同时 `emit('close')` 和 `$emit('open')`**，但 Gallery 侧只监听 `@close`，**相似图导航实际上是断的**（点了会关抽屉，新的 id 不会被打开）。
6. **Chat 页自己实现了一个残缺抽屉**（只有一张图 + 标题），与 ImageDrawer 不一致，且没有详情/修正能力。

**P1 —— 功能存在但不好用**

7. **Gallery 的分类下拉是从当前页图片里 `new Set()` 扒出来的**：翻页换了就变，`/api/categories` 有正式字典却没用；**特有严重误导性**——看起来像全量分类，实际是当前页采样。
8. **检索页结果没有分页**：`limit:60` 硬上限，第 61 条之后永远拿不到，而服务端是支持 cursor 的。
9. **Dashboard 的重复检测千万级风险**：`/api/stats/duplicates` 是全库扫描 dhash 两两比对（Python 侧 O(n²)），前端没有任何提示，用户一点「感知相似」就可能让后端算上几十秒且期间 UI 无任何反馈（无 loading、无进度）。
10. **Jobs 页筛选控件与轮询竞态**：切换下拉触发 `load()`，同时定时 3 秒 `load()`，慢请求会让 UI 状态来回跳。
11. **设置页一屏 16 个分组平铺**：92 个配置项不做任何折叠/搜索，从 G1 滚到 G18 需要滚很久；「显示高级项」是一个全局 checkbox 而不是分组级。
12. **设置页「保存设置」是全量提交**：即便只改了一个开关，也会把 92 项原样 PUT 回去，`bulk_set` 会为每一项写一条审计记录——**一次微调污染整个审计流**。
13. **Entities 详情页的关联图片只显示 `#id`**，没有任何缩略图或文件名，无法知道关联的是哪张图。

**P2 —— 观感与一致性**

14. 空态文案各不相同（「没有图片。先登记目录或上传图片。」/「暂无数据」/「还没有相册」），语气和标点不统一。
15. `.masked` 隐私模式只对 `.ph img` 生效，抽屉大图和相似图不遮。
16. 无加载态可视化：所有请求期间页面静止，只有 Gallery 有一个 `loading` 变量且只用于禁用按钮。
17. 无键盘可达性：抽屉、下拉、批量操作全靠鼠标。

这是本次重写必须消灭的部分。当前只有走 curl 或直接读 SQLite 才能用到：

|---|---|---|---|
| 站内通知 | `GET /api/notices`、`DELETE /api/notices` | **完全无 UI**（库里躺着 37 条） | 顶栏铃铛未读角标 + 下拉面板 + 运维页全量列表 |

| 任务事件级别 | `job_events.level` | 前端只渲染 message | 按级别着色 |

## 4. 数据契约速查（重写时的字段依据）

### 4.1 image 行（`SELECT * FROM images`，列表与详情同源）

```
id, dir_id, path, filename, ext, md5, dhash, width, height, bytes, mtime,
exif_taken_at, dominant_color, analysis_state, category_ai, category_manual,
description_ai, description_manual, has_text, correction_count, last_feedback,
notes, rating, favorite, missing, created_at, updated_at
```

列表额外注入：`score`（融合分）、`thumb`（`/api/thumbs/{id}`）。
详情额外注入：`hidden`、`manual_tags[]`、`ai_tags[]`、`elements[]`、`ocr_text`、`analyses[]`（含 model/tokens_in/tokens_out）、`custom_fields`、`has_thumb`、`thumb`。

⚠️ 列表里**没有** `category` / `description` 这种合并字段——前端渲染时要自己 `category_manual || category_ai || "未分类"`，这正是旧 ImageCard 直接用 `image.category` 导致永远显示「未分类」的原因（隐性 Bug）。

### 4.2 analysis_state 取值

`unanalyzed` → `queued` / `pending` → `running` → `done`，异常分支 `failed`、`skipped`（超大图/隐私）、以及耗尽重试后的任务态 `dead`。
当前库真实分布：**failed 7 / running 1 / skipped 2**。

### 4.3 设置 schema 的 item 结构

```jsonc
{ "key", "label", "type": "int|float|bool|select|text|tags|csv", "default",
  "help", "min", "max", "options": [...], "effective": "on-save|immediate",
  "advanced": bool }
```

绑定类 key（`profile_vision/embed/chat/enhance`）的 `options` 由后端动态拼为 `["default", "@follow", ...档案名]`，且 `free=true` 允许写入列表外的值——前端必须**既能选也能手输**，否则用户无法填任意档案名。

`GET /api/settings` 额外返回 `values`（当前值全体）、`profiles`（档案列表，含已解密的 `api_key` 明文）、`danger_groups: ["G10"]`。
`csv` 类型在 `values` 里已经是**数组**（后端 `get()` 做了 coerce），但 `PUT` 时要发字符串或数组都行（后端再 coerce 一次）。

### 4.4 端点行为细节（容易踩）

- `POST /api/directories` 不带 `?confirm=1` 时返回 `{confirmed:false, estimate:{...}}`；`estimate.registered_id` 非 null 表示路径已登记，此时第二步应改为增量扫描。
- 图库与检索的列表接口（`GET /api/images`、`GET /api/search`）都会先做一层参数扫描，**拒绝** `hidden/include_hidden/with_hidden/show_hidden` 四个参数（命中即抛 `HiddenNotBypassable`），隐藏区只能走 `/api/hidden`。
- `sort` 白名单只有 `id/mtime/rating/taken/created/filename` 六种。
- `DELETE /api/images/{id}?mode=source` 的确认词 **必须等于文件名**（不是<｜hy_place▁holder▁no▁813｜>写メッセージ）。
- `clear_trash` / `clear-index` 的确认词分别是固定字符串 `清空回收站` / `清空索引`。
- `PATCH /api/images/{id}` 里若包含与自定义字段同名的值，会被写入自定义字段表。

## 5. 重写目标（一句话版）

**保留 Vue3 + Vite + 零新运行时依赖的前提下，把散装的 12 个页面重建成一套有令牌、有组件、有状态中心、有错误边界的管理界面，并把上表 14 项「有 API 无 UI」的能力全部补上。**

落到可验证的几条：

1. 任何界面元素都不写死颜色和关键尺寸，全部走 CSS 令牌；**支持亮/暗 + 6 套强调色**，且选择由后端设置持久化。
2. 列表类页面统一走「网格/列表双视图 + 多选 + cursor 无限滚动 + 加载骨架 + 空态」四件套。
3. 全局设置、toast、侧栏模块、通知角标收敛到单例 store，页面上不再出现第二次 `/api/settings` 请求。
4. 所有写操作统一 `try/catch` + toast + 失败不改变省内 UI 状态；危险操作统一走确认弹窗（不再用 `window.confirm` / `window.prompt`）。
5. 92 个配置项分成 16 组，**分组折叠 + 关键字搜索 + 分组级高级项过滤**，保存时只提交脏值。
