# ADR-004：OCR 按需触发（识图判定含文字才追加 OCR）

- 状态：已接受
- 日期：2026-09-28
- 决策者：库主

## 上下文

需求："识图时，OCR 是额外对有文字的图片的操作。"含义是 OCR **不是**每张图的必经阶段，只有"有文字的图片"才需要。图库中大部分图片（照片、插画）并无文字，全量 OCR 会浪费限额与 token。

## 决策

1. VLM 识图 prompt 中增加 `has_text` 布尔判定字段（与 category/description 同一次请求产出）
2. `has_text=false` → **不发起 OCR 请求**（零开销），`ocr_results` 无行
3. `has_text=true` → 按目录 `ocr_policy`（`auto`/`on`/`off`）决定是否追加 OCR 请求，结果写**独立 OCR 表**
4. `has_text` 无论结果都落库 `images.has_text`，供规则引擎第二阶段求值使用
5. OCR 请求与识图共享同一限速器与每日预算（`purpose='ocr'` 单独记账）

## 后果

- ✅ 无文字图零 OCR 成本，限额与预算花在刀刃上
- ✅ OCR 仍是独立表（需求第 5 条），字段语义清晰
- ✅ 与限速（ADR-005）天然协同：总请求数可预期
- ⚠️ 判定依赖 VLM 准确性：漏判可通过目录 `ocr_policy=on` 强制兜底
- ⚠️ 两阶段规则求值（OCR 文本条件）必须延迟到 OCR 完成后复算——已在 F13 设计覆盖

## 替代方案（放弃）

- 全量 OCR：违反"额外操作"的定位，成本 ×N
- 本地文字检测预筛（如 EAST/DB 等）：新增模型依赖与维护成本，违背轻依赖原则
- 仅目录规则指定：无自动判定，用户要逐目录配置，体验差（保留为强制开关而非唯一手段）
